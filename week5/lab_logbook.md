## Changes from previous version

In Week 5, the protocol was modified to model **TLS-style pseudonymous secure channels** and to simplify the protocol while preserving its security goals.

### 1. Fixing the identity provider

The identity provider name was changed from **`IdP` to `idp`** and treated as a fixed agent.
This prevents the intruder from instantiating the identity provider role during verification and reflects the intended architecture with a single trusted identity provider.

### 2. Introducing pseudonymous secure channels

The communication between **A and idp**, and between **A and P**, was replaced with pseudonymous secure channels.
### 3. Retaining cryptography between P and B

The communication between **P and B** still uses explicit cryptographic protection:

```
P -> B: { ... }inv(pk(P))
B -> P: {{ ... }inv(pk(B))}pk(P)
```

This is necessary because pseudonymous channels do not authenticate the client identity.
Therefore, the request from `P` must still be signed, and the response from `B` must be signed and encrypted.

### 4. Adding role constraints

A constraint was introduced:

```
where B != P
```

This prevents the roles `B` and `P` from being instantiated as the same agent.
Such cases are unrealistic and can lead to artificial attacks during model checking.

### 5. Simplifying message contents

Compared to Week 4, the protocol messages were simplified while keeping the necessary bindings:

```
f3(B, P, token, N_P_req)
f4(B, P, N_P_req, Photos)
```

The identities and nonce ensure proper session binding and prevent replay or mix-up attacks.

# Modeling Considerations

### TLS abstraction

TLS communication is modeled using **pseudonymous secure channels** instead of explicitly modeling encryption and key exchange.

This abstraction assumes that confidentiality and integrity are already provided by the transport layer.

### Identity binding

The identities `B` and `P` are included in the protocol messages to ensure that responses correspond to the correct communication partners.

### Freshness

The nonce `N_P_req` generated by `P` ensures freshness of requests and responses, since pseudonymous channels alone do not guarantee protection against replay attacks.

## Problems Encountered

### Loss of authentication when overusing channels

An early design replaced the `P → B` communication with pseudonymous channels.
However, this prevented `B` from verifying that the request originated from the authorized service `P`.
To solve this issue, explicit signatures were retained for the communication between `P` and `B`.

### Mix-up risks during protocol simplification

When simplifying the protocol messages, removing identity bindings created potential mix-up attacks where messages from different sessions could be incorrectly combined.
Including `B` and `P` in the message formats resolved this problem.

### Long verification time in OFMC

During verification, the protocol required a very long running time in OFMC.
This is caused by the **state-space explosion problem**, which arises from multiple sessions and nested cryptographic structures.

Several steps were taken to mitigate this issue:

* simplifying message formats
* removing unnecessary fields

Although these optimizations reduced the search space, verification for higher session bounds still required significant time.
